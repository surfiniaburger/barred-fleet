# Spec: BARRED-Fleet Invariant Scorecard Panel

## Objective
Expose the deterministic B-gate invariants as a first-class scorecard in the `/demo` UI and product run report path.

The user is a judge, reviewer, or operator who needs to see why a BARRED run was accepted without trusting model narration. Success means the demo can show the same invariant-style evidence currently visible in local/Looker-style analytics directly from Cloud Run-backed reports.

This is a reporting slice only. It must not trigger live model calls, change acceptance logic, or inflate local benchmark claims into cloud production claims.

## Current State
- `/demo` already renders high-level cards for B-gate, accepted rows, verifier parse OK, and verifier pass.
- `/demo` already uses `/runs/{run_id}/report` for fresh/live/dry-run results.
- `/runs/{run_id}/report` already preserves `b_gate.selected_metrics` when artifact-backed B-gate output exists.
- `/demo/report` currently compresses B-gate metrics into a small subset and does not expose the complete `selected_metrics` map cleanly.
- Looker/Data Studio can already visualize Firestore-flattened fields, but `/demo` does not yet present those invariants as a product-facing scorecard.

## Code Style
Use small adapter functions that format existing facts rather than recomputing B-gate decisions in the UI layer.

```python
def _invariant_scorecard(selected_metrics: dict[str, Any]) -> list[dict[str, Any]]:
    return [
        {
            "key": "b0_structural_completeness_pass_rate",
            "label": "Structural completeness",
            "value": selected_metrics.get("b0_structural_completeness_pass_rate"),
            "format": "percent",
            "direction": "higher_is_better",
        },
    ]
```

Conventions:
- Keep raw metric keys available for machine consumers.
- Add labels/formats for humans.
- Treat missing values as `None`/`n/a`, not as zero.
- Do not expose raw seed text or raw vulnerability snippets.
- Do not let UI labels become new acceptance logic.

## Invariant Metrics
The initial scorecard should render these B-gate metrics when present:

| Metric Key | Label | Format | Interpretation |
| --- | --- | --- | --- |
| `total_rows` | Total accepted corpus rows | integer | Number of rows evaluated by the deterministic acceptance gate. |
| `accepted_rows` | Accepted rows | integer | Number of rows that survived the acceptance pipeline. |
| `b0_structural_completeness_pass_rate` | Structural completeness | percent | Accepted rows with required structural fields. |
| `b1_unsupported_in_accepted_rate` | Unsupported accepted rate | percent | Accepted rows still marked unsupported; lower is better. |
| `b1_inconclusive_in_accepted_rate` | Inconclusive accepted rate | percent | Accepted rows still marked inconclusive; lower is better. |
| `b2_anchor_match_rate` | Anchor match rate | percent | Accepted rows whose evidence anchors match expected predicate evidence. |
| `verifier_parse_ok_rate` | Verifier parse OK | percent | Verifier outputs that parse into the expected schema. |
| `verifier_pass_rate` | Verifier pass | percent | Verifier pass rate over audited rows. |
| `accepted_attempt_logic_error_rate` | Attempt logic error rate | percent | Logic-error rate in accepted attempt artifacts; lower is better. |
| `accepted_corpus_logic_error_rate` | Corpus logic error rate | percent | Logic-error rate in accepted corpus artifacts; lower is better. |

## Reporting Contract
`/demo/report` should include:

```json
{
  "b_gate": {
    "selected_metrics": {
      "accepted_rows": 5,
      "b2_anchor_match_rate": 1.0
    },
    "invariant_scorecard": [
      {
        "key": "b2_anchor_match_rate",
        "label": "Anchor match rate",
        "value": 1.0,
        "format": "percent",
        "direction": "higher_is_better"
      }
    ]
  }
}
```

`/runs/{run_id}/report` should either:
- preserve the artifact-backed `b_gate.selected_metrics`, and
- include the same `b_gate.invariant_scorecard`; or
- return an explicit unavailable state for planned/running/dry-run reports.

Unavailable reports should say the scorecard is not available until a final B-gate artifact or deterministic receipt exists. They should not show missing artifact errors as product failures.

## UI Behavior
Add an `Invariant Scorecard` panel to `/demo`.

For curated runs:
- Render the complete scorecard from `/demo/report.b_gate.invariant_scorecard`.
- Preserve current top cards as the quick summary.

For fresh/live/dry-run results:
- Render the complete scorecard from `/runs/{run_id}/report.b_gate.invariant_scorecard` when available.
- If unavailable, render `Invariant scorecard: pending final B-gate artifacts`.
- Keep dry-run and live refusal flows non-scary and clearly labelled.

Suggested columns:
- Invariant
- Value
- Direction
- Source key

## Testing Strategy
Unit tests first, no paid model calls.

Required tests:
- `build_demo_report()` includes `b_gate.selected_metrics` and `b_gate.invariant_scorecard` for the curated run.
- `build_demo_html()` includes the `Invariant Scorecard` panel and JavaScript rendering hook.
- `/demo/report` returns the invariant scorecard through FastAPI.
- `/runs/{run_id}/report` includes `b_gate.invariant_scorecard` for artifact-backed completed runs.
- Planned/running reports keep `selected_metrics={}` and expose an unavailable scorecard state without artifact-error language.

Do not add live Gemini calls to verify this slice.

## Boundaries
- Always: preserve deterministic B-gate as the only acceptance authority.
- Always: keep raw seed/code text out of `/demo` and report payloads.
- Always: treat missing metrics as unavailable, not failed.
- Always: keep `/demo/report` backward compatible with existing fields.
- Ask first: changing B-gate thresholds, metric definitions, or Firestore document shape.
- Ask first: adding Looker/Data Studio, BigQuery, or new Google Cloud dependencies.
- Never: create metrics by model narration.
- Never: count local benchmark invariants as fresh cloud run volume unless they came from promoted cloud artifacts.
- Never: trigger paid model calls from scorecard rendering.

## Success Criteria
- `/demo` visibly contains an `Invariant Scorecard` panel.
- `/demo/report` exposes the full `selected_metrics` map and human-readable scorecard rows.
- `/runs/{run_id}/report` exposes the same scorecard shape for artifact-backed completed runs.
- Dry-run/planned reports show scorecard unavailability without scary missing artifact failures.
- Existing `make verify-demo` and `make verify-fresh-demo` still pass.
- Unit tests pass with `uv run pytest tests/unit/test_demo.py tests/unit/test_run_lifecycle.py -q`.

## Open Questions
1. Should the scorecard include only B-gate metrics, or also safety receipt fields like Model Armor and Agent Gateway status?
   - Recommendation: keep safety controls in their existing panel; the scorecard should stay B-gate/invariant-only.
2. Should Looker/Data Studio use this `/demo` scorecard contract directly?
   - Recommendation: no. Keep Looker on Firestore/BigQuery-style flattened rows; `/demo` is for human proof, not BI extraction.
3. Should local 500-seed analytics be shown next to cloud runs?
   - Recommendation: only if clearly labelled as local/offline evaluation. Do not blend local and cloud counts in one scorecard.
